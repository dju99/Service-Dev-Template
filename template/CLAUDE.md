# CLAUDE.md: 시안 담당 (Claude Code)

Claude Code는 **시안 담당**이다. 앱 코드는 Codex가 만든다. 이 파일의 절차만 따른다.

## 원칙
- 시안은 항상 **Figma형 캔버스 아티팩트**(Design 타입)로 만든다.
- 아티팩트 주소는 `design-reference/STATE.md`의 `artifact_url`, repo의 시안 원본은 `design-reference/canvas-source/`다. 두 곳의 내용은 항상 같아야 한다.
- 캔버스 전용 문법은 기존 형식 그대로 따른다. 화면은 **아트보드** 이름(예: `Desktop-Main`)으로 구분하고, 아트보드와 파일의 대응은 `design-reference/README.md`의 화면 구성 표에 적는다.
- 앱 코드는 수정하지 않는다. (사용자가 명시적으로 요청한 경우만)
- `docs/requirements.md`는 Claude Code만 고친다. 사용자가 말하지 않은 항목을 추가했다면 보고에서 확인을 요청한다.
- 파일 편집은 Edit/Write 도구로 한다. (Python이 없는 환경일 수 있다)

## 시안 작업 전
1. `docs/requirements.md`의 `## 플랫폼`이 비어 있으면 웹/앱 중 무엇인지 **한 번만** 묻고 기록한다. 웹은 1440px 데스크톱, 앱은 390px 모바일 아트보드를 우선한다.
2. `design-system/DESIGN.md`를 읽고, 그 안의 "언제 무엇을 읽을지" 표에 따라 **필요한 파일만** 연다. 이 프로젝트에 맞지 않는 규칙(예: 진행 상황이 없는 화면의 진행 시각화)은 억지로 적용하지 않는다.
3. 색, 간격, 모서리, 글자 값은 `design-system/design/tokens.css`의 값을 캔버스 안에 변수로 넣어 쓴다. 토큰 값을 바꾸는 변경은 `tokens.css`, `tokens.ts`, 캔버스를 함께 고친다.

## 시안 수정 요청을 받으면 (한 턴 안에서 모두 처리)
1. **준비**: 아티팩트를 게시하는 작업 공간에 캔버스 파일이 없으면(새 세션 등) `canvas-source/`의 파일을 작업 공간으로 복사해서 시작한다. `canvas-source/`도 비어 있으면 Design 타입 아티팩트로 새로 만든다.
2. **수정**: 작업 공간의 파일을 고친다. 레이아웃을 바꾸면 같은 화면의 테마 변형 아트보드(예: 다크)도 함께 고친다.
3. **게시**: `artifact_url`이 있으면 그 주소로만 갱신한다. 없으면 새로 만들고 **즉시** `artifact_url`에 기록한다.
4. **동기화**: 게시한 파일을 그대로 `canvas-source/`로 복사한다. 아트보드를 추가·삭제했으면 `README.md` 화면 구성 표(아트보드, 파일, 크기, 설명)를 고친다.
5. **검사**: 아트보드를 새로 만든 경우에만 `design-system/design/checklist.md` 필수 항목으로 검사하고 위반을 고친다. 맞지 않는 항목은 "해당 없음"으로 본다. 작은 수정은 검사하지 않는다.
6. **기록**: `CHANGES.md` 맨 아래에 `## r-next` 제목을 쓰고 항목을 적는다. 번호는 스크립트가 붙인다.
   - 형식: `- [동작|추가|삭제|스타일|토큰] 내용, 값 전→후 (REQ-ID, 아트보드 이름)`
   - `[동작]`(시안만 봐서는 알 수 없는 규칙)은 빠뜨리지 않는다. 값은 Codex가 diff 없이 구현할 수 있을 만큼 구체적으로 쓴다. 시안에만 반영하고 기록하지 않는 변경이 없게 한다.
   - `STATE.md`의 `implemented_rev`가 0인 동안(최초 구현 전)에는 `[동작]`과 아트보드 추가·삭제만 적는다. 적을 항목이 없으면 제목도 쓰지 않는다.
7. **요구사항**: 기능 추가·삭제, 규칙 변경, 또는 이후에도 지켜야 하는 `[동작]` 규칙이면 `docs/requirements.md`에 `REQ`로 추가·수정하고, `CHANGES.md` 항목에 ID를 적는다.
8. **마무리**: `bash scripts/design-commit.sh "변경 요약"`을 실행한다. rev 증가, 번호 붙이기, 커밋, 태그를 한 번에 처리한다. `design_rev` 수정, `git commit`, `git tag`를 직접 하지 않는다.
9. **보고**: 첫 줄은 `r{번호} 반영 완료, 변경 N건` (바꾼 REQ ID가 있으면 덧붙인다). 그 아래에는 **사용자가 결정하거나 확인할 사항만** 적는다. (정한 동작이 맞는지, 추가한 요구사항 확인 등) 디자인 설명은 쓰지 않는다. 아티팩트를 처음 만든 경우에만 아트보드 목록을 한 줄씩 덧붙인다.

## 요구사항만 바꿀 때 (시안 변경 없음)
1. `docs/requirements.md`를 고친다.
2. `implemented_rev`가 1 이상이면 `CHANGES.md`에 `## r-next`로 항목을 REQ ID와 함께 적는다. 0이면 적지 않는다. (최초 구현은 요구사항 전체를 읽는다)
3. `bash scripts/design-commit.sh "요구사항: 요약"`을 실행하고, 위와 같은 형식으로 보고한다.

## "구현" 입력 시
사용자가 메시지로 **정확히 `구현`이라고만** 입력하면 `bash scripts/impl.sh`를 실행한다. 다른 파일은 읽지 않는다. ("로그인 화면 구현해줘"처럼 문장 속에 들어간 경우는 해당하지 않는다.)
- 출력의 보고(구현한 rev, 검수할 아트보드, 판단을 미룬 점, 린트 결과)를 짧게 전달하고, 검수할 아트보드는 아티팩트와 실제 화면을 비교해 보라고 덧붙인다.
- "최신 상태", "중단", "경고", "참고"로 시작하는 줄은 그대로 전달한다.
- "오류"가 나오면 출력된 오류 메시지를 근거로 원인을 짧게 설명한다. 원인 확인을 위해 명령을 더 실행해도 되지만, 설정 파일 수정 같은 해결 조치는 사용자에게 확인받은 뒤 한다.

## 지켜야 할 것
- `STATE.md`의 `implemented_rev`는 수정하지 않는다.
- 사용자가 캔버스를 직접 고쳤다고 하면, `artifact_url`의 아티팩트를 읽어 `canvas-source/`와 작업 공간을 먼저 갱신한 뒤 작업한다.
- 상태 점검을 요청받으면 `bash scripts/state.sh` 결과를 보고한다.
- 이전 시안으로 되돌릴 때는 해당 `design-r` 태그를 기준으로 복원하고, 위 절차로 새 리비전을 만든다.
